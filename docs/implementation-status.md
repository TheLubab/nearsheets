Public RPC recovery (2026-11-13): Public balance and contract reads are paced per endpoint (at most three active calls, starts at least 250ms apart). On a transient transport failure, HTTP rate limit or timeout, the default public RPC falls back once to FASTNEAR on the same network (`https://free.rpc.fastnear.com` / `https://test.rpc.fastnear.com`). Failed endpoints cool down for 30 seconds. Each SDK attempt is limited to six seconds within the existing 15-second query wait budget, including queue time. There are no unbounded retries; large queues can reach that budget. Cancellation and contract/account errors do not trigger fallback. A configured custom RPC remains authoritative for its configured network and does not leak its reads to a public fallback. Wallet submission and transaction reconciliation are unchanged. The fallback URLs are listed in the [official NEAR RPC provider documentation](https://docs.near.org/api/rpc/providers), checked 2026-11-13; browser CORS/reachability was not probed. Mocked tests exercise the installed SDK HTTP 429 path, the reported Firefox-style NetworkError, shared endpoint cooldown, paced starts/concurrency, queued cancellation, timeout fallback, permanent-error propagation, exhausted fallbacks and custom-network isolation. Typecheck, production build and the focused read/runtime/cell/env checks passed. No RPC probes or blockchain transactions were performed. A cold browser load still needs user confirmation.


Read scheduling (2026-11-13): replaced network-awaiting formula evaluation with background reads and native value-object results. Pending cells propagate `#GETTING_DATA`; completed results dirty their source cells and dependents through the installed Univer 1.4 trigger, with a 20ms completion batch. Real-engine mocked-service tests verify fast reads and dependent arithmetic render before a deliberately unresolved read, exact text/spills/errors remain usable, edited inputs cancel unused work, and Stop produces a stopped state without automatic restart. Metadata and catalog caching, parallel FT reads, selected refresh isolation and bounded waits have focused tests. Blockchain reads run in the background: independent cells can finish while others are loading. Pending cells show `#GETTING_DATA`, which propagates through arithmetic rather than becoming zero (an explicit `IFERROR` may handle it). Results trigger batched recalculation of their cells and dependents, rather than the whole workbook. Identical reads share in-flight requests. Balances and contract reads cache for 30 seconds, verified FT metadata and the shared Intents token catalog for five minutes, and quotes/status for five seconds. Selected refresh invalidates the selected dependency keys and all cells sharing those keys; unrelated pending reads continue. Each request has a 15-second wait limit, without automatic query retries; RPC reads use one SDK attempt. Edits cancel unused reads, and Stop leaves an explicit stopped state until refresh. Intents fetches support transport abort; the installed NEAR SDK does not expose a fetch signal, so an already dispatched RPC request may finish in the background after cancellation or timeout, with its result ignored. These are freshness windows, not background polling intervals.
